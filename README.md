# Plans/Finance

Приложение для контроля финансов и планирования бюджета: составляйте план трат
на месяц, копите на цели, вносите ежедневные/еженедельные траты и следите за
прогрессом — с красивым тёмным интерфейсом и мотивацией при каждом заходе.

Реализовано как **PWA (Progressive Web App)** — веб-приложение, которое
устанавливается на телефон как обычное приложение (иконка на главном экране,
офлайн-режим), но без публикации в App Store/Google Play. Подробное объяснение
выбора платформы — в разделе [«Веб vs мобильное приложение»](#веб-vs-мобильное-приложение).

## Архитектура

```
┌─────────────────────┐        HTTPS/JSON        ┌──────────────────────┐        SQL         ┌──────────────┐
│   Frontend (PWA)     │  ──────────────────────▶ │   Backend (FastAPI)  │ ─────────────────▶ │  PostgreSQL  │
│  React + TypeScript  │  ◀────────────────────── │   Python 3.12+       │ ◀───────────────── │              │
│  Vite + Tailwind     │      JWT в заголовке      │  SQLAlchemy + Alembic│                    └──────────────┘
└─────────────────────┘                            └──────────────────────┘
```

- **Frontend** — React 18 + TypeScript, собирается Vite, стилизован Tailwind CSS.
  Хранит только UI-состояние и токены авторизации; вся бизнес-логика и данные — на backend.
- **Backend** — FastAPI (Python), асинхронный, отвечает за аутентификацию,
  бизнес-правила (например, движок рекомендаций бюджета) и работу с БД.
- **База данных** — PostgreSQL, единственное постоянное хранилище всех данных
  пользователей (см. ниже почему).

### Почему такой стек

| Слой | Выбор | Почему |
|---|---|---|
| БД | PostgreSQL | Надёжная, бесплатная, промышленный стандарт; точные типы для денег (Numeric), даты, перечисления; отличные бесплатные managed-хостинги (Neon, Supabase, Railway, Render) |
| Backend | FastAPI (Python) | Быстрый асинхронный фреймворк, автоматическая валидация данных (Pydantic) и автогенерируемая документация API (`/docs`); вы говорили, что вам удобнее работать в Python |
| ORM/миграции | SQLAlchemy 2.0 + Alembic | Модели БД описываются как обычный Python-код; Alembic отслеживает изменения схемы версионируемыми миграциями — легко накатывать/откатывать изменения структуры БД |
| Frontend | React + TypeScript + Vite | Самый популярный стек для быстрых, отзывчивых интерфейсов; TypeScript исключает целый класс ошибок за счёт типизации данных, приходящих с backend |
| Стили | Tailwind CSS | Позволяет быстро и последовательно выдерживать тёмную минималистичную тему без написания сотен строк ручного CSS |
| PWA | vite-plugin-pwa | Готовое решение для service worker (офлайн-кэш) и manifest (установка на телефон) |

## Схема базы данных

Все данные пользователей и их настройки хранятся в PostgreSQL. Ниже — таблицы
и связи между ними.

```
users ──1───1── user_settings
  │
  ├──1───N── categories  (user_id = NULL → системная категория, видна всем)
  │
  ├──1───N── monthly_plans ──1───N── plan_allocations ──N───1── categories
  │                 │
  │                 └──1───N── goal_contributions ──N───1── goals
  │
  ├──1───N── goals ──1───N── goal_contributions
  │
  └──1───N── transactions ──N───1── categories

motivational_quotes  (самостоятельная таблица, не привязана к пользователю)
```

### Таблицы подробно

**`users`** — учётная запись: `id (UUID)`, `email` (уникальный), `hashed_password`
(bcrypt-хеш, пароль в открытом виде никогда не хранится), `full_name`, `is_active`.

**`user_settings`** — персональные настройки (1:1 с `users`), отделены от `users`,
чтобы не раздувать таблицу аутентификации: `default_currency`, `entry_frequency`
(daily/weekly/custom), `custom_frequency_days`, `motivational_quotes_enabled`, `theme`.

**`categories`** — категории трат/доходов. `user_id = NULL` означает системную
(preset) категорию, видимую всем пользователям (создаются один раз через
`app/services/seed.py`); `user_id = <id>` — категория, созданная конкретным
пользователем и видимая только ему. Поле `is_essential` помечает "обязательные"
траты (жильё, еда) — используется движком рекомендаций.

**`monthly_plans`** — план на конкретный месяц: `user_id`, `month` (всегда первое
число месяца), `total_income`, `currency`. Уникальный индекс `(user_id, month)`
гарантирует ровно один план на месяц у пользователя.

**`plan_allocations`** — строки плана: сколько денег выделено на каждую
категорию в рамках месяца. Связь `monthly_plans` → `plan_allocations` → `categories`.

**`goals`** — финансовые цели пользователя: `name`, `target_amount`,
`current_amount` (обновляется при каждом пополнении), `deadline`, `status`
(active/completed/archived).

**`goal_contributions`** — история пополнений цели, опционально привязана к
конкретному `monthly_plan_id` (когда пополнение сделано "по плану" при
сохранении бюджета на месяц) — так можно посмотреть, сколько отложено на цель
именно в конкретном месяце.

**`transactions`** — отдельная запись о трате/доходе: `category_id`, `type`
(expense/income), `amount`, `currency`, `occurred_on` (дата), `description`.
Самая часто читаемая/записываемая таблица — есть составной индекс
`(user_id, occurred_on)` для быстрых выборок за период.

**`motivational_quotes`** — мотивационные фразы, показываемые при заходе в
трекер; хранятся в БД (не хардкодятся на фронтенде), чтобы можно было
добавлять новые без обновления приложения.

### Почему такая структура

- **UUID вместо числовых id** — id нельзя перебрать/угадать, поэтому их можно
  безопасно использовать прямо в URL API (`/api/goals/<id>`) без риска, что
  один пользователь подставит id и получит чужие данные (авторизация всё
  равно всегда проверяется на backend отдельно, это дополнительный уровень).
- **Numeric(14,2) для денег**, а не float — исключает ошибки округления
  copeck/цента, характерные для чисел с плавающей запятой.
- **Мультивалютность**: у `user_settings` есть `default_currency` (валюта по
  умолчанию для форм), но каждая транзакция/цель/план хранит **свою** валюту.
  Специально не конвертируем валюты автоматически (курсы валют нужно было бы
  тянуть из внешнего API и это отдельная зона ответственности) — сравнения
  план/факт корректны, потому что план и связанные с ним траты по умолчанию
  ведутся в одной валюте.
- **Миграции через Alembic** — при любом изменении моделей (например,
  добавление нового поля) создаётся новый файл миграции, который можно
  применить (`alembic upgrade head`) или откатить (`alembic downgrade -1`) —
  так БД в продакшне всегда переходит между версиями предсказуемо, без
  ручных ALTER TABLE.

## Функциональность и экраны

### Два главных экрана

1. **«Мой план»** (`/plan`) — планирование бюджета на месяц:
   - Указываете ожидаемый доход.
   - Нажимаете «Помочь распределить бюджет» — приложение предлагает суммы по
     каждой категории (см. [движок рекомендаций](#движок-рекомендаций-бюджета)).
   - Корректируете суммы по каждой категории трат вручную.
   - Указываете, сколько отложить в этом месяце на каждую из своих целей.
   - Видите итог: доход − (траты + отчисления на цели) = свободный остаток
     (подсвечивается красным, если бюджет превышает доход).

2. **«Трекер»** (`/tracker`) — внесение трат и контроль прогресса:
   - При заходе показывается мотивационная фраза.
   - Переключатель периода: день / неделя / месяц (по умолчанию — как
     настроено в «Настройки → Периодичность»), с навигацией вперёд/назад.
   - Кнопка «+» открывает форму добавления траты/дохода: категория, сумма,
     дата, комментарий.
   - Вкладка «Обзор»: таблица план/факт по каждой категории (с индикатором
     превышения) + таблица прогресса по всем целям.
   - Вкладка «Операции»: список всех внесённых записей за период с
     возможностью удаления.

### Экраны настроек (для удобства, не основные)

- **Профиль** — имя, email (только просмотр), смена пароля.
- **Категории** — просмотр всех категорий (готовые + свои), добавление своих
  категорий с выбором цвета и пометкой "обязательная трата", удаление своих
  категорий (системные защищены от изменения/удаления).
- **Мои цели** — создание/удаление целей, просмотр прогресса.
- **Периодичность и вид** — валюта по умолчанию, как часто вносить траты
  (день/неделя/свой интервал в днях), включение/выключение мотивационных фраз.

### Движок рекомендаций бюджета

Реализован в `backend/app/services/recommendations.py`, два режима:

1. **Есть история трат (3+ месяца)** — считается средняя трата по каждой
   категории за последние 3 месяца, суммы масштабируются так, чтобы
   уложиться в 80% дохода (гарантируя минимум 20% на сбережения).
2. **Нет истории (новый пользователь)** — используется классическое правило
   личных финансов **50/30/20**: 50% дохода на обязательные траты, 30% на
   необязательные, 20% на сбережения/цели. Сумма внутри каждой группы делится
   между существующими категориями пользователя.

## Дизайн-система

Тёмная, минималистичная, но не блеклая тема (см. `frontend/tailwind.config.js`):

- **Фон** — почти чёрный тёплый тон `#0B0B0F` (не чистый `#000`, чтобы глаза
  меньше уставали и была видна глубина карточек).
- **Поверхности карточек** — `#15151C` / `#1D1D26`, чуть светлее фона.
- **Акцентные цвета** — каждый со своим смыслом, без визуального шума:
  - фиолетово-синий `#7C5CFF` — основные действия;
  - зелёный `#00E38C` — доходы, достигнутые цели, "всё хорошо";
  - розово-красный `#FF5470` — траты, превышение бюджета;
  - янтарный `#FFB020` — предупреждения.
- **Типографика** — шрифт Manrope, крупные заголовки, много "воздуха" между
  блоками, отсутствие лишних разделительных линий и декоративных элементов.
- **Mobile-first**: интерфейс ограничен по ширине как на телефоне
  (`max-w-md`) даже в браузере на десктопе — это специально, чтобы выглядело
  как настоящее мобильное приложение.

## Как запустить локально

### Вариант А — одной командой через Docker (рекомендуется)

Нужен установленный [Docker Desktop](https://www.docker.com/products/docker-desktop/).

```bash
docker compose up --build
```

После сборки:
- Приложение: http://localhost:8080
- API и его документация (Swagger UI): http://localhost:8000/docs

При первом запуске backend-контейнер сам применит миграции и заполнит базу
стартовыми категориями и мотивационными фразами.

### Вариант Б — запуск вручную (для разработки)

**1. PostgreSQL** — поднимите локально или через Docker:

```bash
docker run --name plans-finance-db -e POSTGRES_USER=plans_user \
  -e POSTGRES_PASSWORD=plans_password -e POSTGRES_DB=plans_finance \
  -p 5432:5432 -d postgres:16-alpine
```

**2. Backend:**

```bash
cd backend
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt
copy .env.example .env   # на Windows; на macOS/Linux: cp .env.example .env
# откройте .env и при необходимости поменяйте DATABASE_URL / JWT_SECRET_KEY

alembic upgrade head          # применить миграции (создать таблицы)
python -m app.services.seed   # заполнить стартовые категории и цитаты
uvicorn app.main:app --reload --port 8000
```

Backend будет доступен на http://localhost:8000, документация API — на
http://localhost:8000/docs.

**3. Frontend** (в отдельном терминале, нужен установленный [Node.js](https://nodejs.org/) 20+):

```bash
cd frontend
npm install
npm run dev
```

Откройте http://localhost:5173 — Vite автоматически проксирует запросы `/api`
на backend (порт 8000), см. `frontend/vite.config.ts`.

### Установка на телефон (проверка PWA)

1. Разверните приложение на HTTPS-адресе (см. раздел «Хостинг» — на
   `localhost` тоже работает для локальной проверки в мобильном браузере
   через тот же Wi-Fi, используя IP компьютера).
2. Откройте адрес в браузере телефона (Chrome/Safari).
3. В Chrome (Android) появится баннер/пункт меню «Добавить на главный
   экран». В Safari (iOS) — кнопка «Поделиться» → «На экран Домой».
4. Приложение появится как отдельная иконка, откроется в полноэкранном
   режиме без адресной строки браузера.

> Обратите внимание: сгенерированные иконки (`frontend/public/icons/`)
> сейчас имеют одинаковый файл для 192×192 и 512×512 — браузеры это
> нормально масштабируют, но для идеальной чёткости на всех устройствах
> рекомендуется позже сгенерировать точные размеры (например, через
> https://realfavicongenerator.net/).

## Хостинг и деплой

Раз вы попросили посоветовать — вот бесплатный/дешёвый вариант, которого
достаточно для начала (личное или небольшое пользовательское приложение):

| Компонент | Рекомендация | Почему |
|---|---|---|
| PostgreSQL | [Neon](https://neon.tech) или [Supabase](https://supabase.com) | Есть бесплатный тариф, managed-БД (не нужно администрировать сервер), выдают готовую строку подключения — просто вставить в `DATABASE_URL` |
| Backend (FastAPI) | [Railway](https://railway.app) или [Render](https://render.com) | Автодеплой из GitHub-репозитория, бесплатный тариф для небольшой нагрузки, умеют собирать проект по вашему `Dockerfile` |
| Frontend (PWA) | [Vercel](https://vercel.com) или [Netlify](https://netlify.com) | Бесплатный хостинг статики с HTTPS "из коробки" (обязательно для PWA — service worker требует HTTPS), автодеплой при пуше в git |

Примерный порядок действий:
1. Создать БД на Neon/Supabase → скопировать `DATABASE_URL`.
2. Задеплоить папку `backend/` на Railway/Render, указав переменные окружения
   из `backend/.env.example` (обязательно сменить `JWT_SECRET_KEY` на
   случайный длинный секрет).
3. Задеплоить папку `frontend/` на Vercel/Netlify, указав переменную
   `VITE_API_BASE_URL` = адрес задеплоенного backend (например
   `https://plans-finance-api.up.railway.app/api`).
4. Открыть адрес фронтенда с телефона и установить как PWA (см. выше).

Когда решите, что нужен настоящий нативный маркетинг-листинг в App
Store/Google Play — существующий backend менять не придётся: PWA можно
"обернуть" в нативную обёртку через [Capacitor](https://capacitorjs.com/)
без переписывания бизнес-логики.

## Веб vs мобильное приложение

Как и договаривались — реализовано веб-приложение (PWA) вместо нативного
мобильного, вот почему это разумный выбор для этого проекта:

- **Один код — все платформы.** PWA работает одинаково в браузере на
  компьютере и на телефоне (Android и iOS), не нужно поддерживать 2 отдельных
  нативных проекта (Swift для iOS + Kotlin для Android).
- **Устанавливается на телефон как обычное приложение** — иконка на главном
  экране, полноэкранный режим без браузерной строки, работает офлайн
  (service worker кэширует интерфейс).
- **Мгновенные обновления** без публикации новых версий через сторы и
  ожидания модерации.
- **Нет затрат на аккаунты разработчика** (Apple Developer Program — $99/год,
  Google Play — разовый взнос) и на прохождение ревью в сторах.
- Если в будущем понадобятся глубоко нативные возможности (push-уведомления
  с богатым форматированием, виджеты на главном экране, биометрия) —
  сегодняшний backend и весь бизнес-код переиспользуются, меняется только
  обёртка (Capacitor/React Native), а не архитектура целиком.

## Известные ограничения и что делать дальше

Эта версия — полностью рабочая основа приложения, документированная и готовая
к запуску, но при подготовке есть особенности окружения, о которых стоит знать:

- Код backend проверен на синтаксическую корректность (`python -m py_compile`
  прошёл без ошибок по всем файлам), но **не запускался вживую** с реальной
  PostgreSQL в этой среде разработки — окружение без доступа к установке
  пакетов (`pip install`) и без Docker/Node.js. Перед первым запуском
  обязательно выполните шаги из раздела [«Как запустить локально»](#как-запустить-локально)
  и, если что-то пойдёт не так, пришлите мне текст ошибки — быстро исправим.
- Иконки PWA (`frontend/public/icons/`) — один сгенерированный файл,
  продублированный на 192×192 и 512×512; работает, но для идеальной чёткости
  стоит позже сделать точные размеры.
- Курсы валют не конвертируются автоматически — при необходимости можно
  добавить интеграцию с внешним API валютных курсов (например
  exchangerate.host) в `backend/app/services/`.
- Восстановление пароля по email (забыли пароль) не реализовано — потребует
  подключения почтового сервиса (например SendGrid/Postmark) для отправки
  писем со ссылкой сброса; готов добавить по запросу.
- Push-уведомления (напоминание "внесите траты") не реализованы — это
  естественное следующее улучшение поверх service worker, который уже
  подключён.
